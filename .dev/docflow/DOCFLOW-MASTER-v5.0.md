# DOCFLOW — Master Plan v5.0 (Консолидирана архитектура)

> **Статус:** Каноничен документ. Този файл заменя/надгражда v1.0–v4.3 и е единственият източник на истина напред.
> **Цел:** Да върне в центъра **оригиналното изискване** (йерархията с променливи), да вземе **най-доброто** от всяка версия и да остане **реалистично** за Home Assistant add-on (единичен Node.js процес, SQLite, без външни зависимости).

---

## 0. Какво се променя спрямо v4.x и защо

Поредицата v4.0–v4.3 (DDD, Multi-Tenancy, Zero Trust) е ценна като **визия за мащабиране**, но направи една фундаментална грешка: замени ядрото на проекта с generic enterprise шаблон — `data JSONB`, microservices-ready схеми, PostgreSQL/Kafka/K8s/HSM. Това **отдалечи** проекта от оригиналното изискване.

**Ядрото на DOCFLOW е едно и е недоговаряемо:**

> Всяко поле от всеки профил е **променлива** с композитен ключ
> `{prefix}-{ID_db}-{id_gruppe}-{field}`, а група профили се обединява под
> стабилен `id_gruppe`. Профилите се **генерират автоматично** при създаване на папка;
> записите могат да съществуват **без папка (orphan)** и да се асоциират по-късно.

Всичко останало — гъвкавост (v3.0), домейн модел (v4.1), multi-tenancy (v4.2), security (v4.3) — се подчинява на това ядро, а не го замества.

**Правилото на v5.0:** *„Конфигурируемо ядро, не enterprise шаблон. Метаданните дефинират схемите, а променливите държат стойностите."*

## 1. Ядрото (НЕДОГОВАРЯЕМО)

### 1.1 Йерархия

```
Група (id_gruppe)                       ← стабилен идентификатор на "досие"
   └── Профил (prefix: 1000..5000)      ← схема/тип, генерира се автоматично
         └── Поле (field)                ← една променлива
               └── Стойност              ← variable_value
```

Композитен ключ на всяка променлива:

```
{prefix}-{ID_db}-{id_gruppe}-{field}
   │        │         │          │
   │        │         │          └─ име на полето (напр. "name", "egn", "phone")
   │        │         └──────────── стабилен ключ на групата (не mutable label)
   │        └────────────────────── ID на базата/инстанцията (изолация между БД)
   └─────────────────────────────── префикс на профила (тип на данните)
```

### 1.2 Профили (автогенерирани)

| prefix | Профил           | Предназначение                        |
| ------ | ---------------- | ------------------------------------- |
| 1000   | Указател         | Справочни записи (от Directory)       |
| 1001   | Служител         | Хора/контакти                         |
| 2000   | Картотека        | Документи/досиета (от Cabinet)        |
| 3000   | Портали          | Портални връзки/QR (от Portals)       |
| 4000   | Текстове         | Стандартни/служебни текстове          |
| 5000   | Шаблони          | Шаблони за документи                  |

Схемата на всеки профил е **metadata-driven** (вж. §3): тя декларира `fields` и техните типове, а не е зашита в код.

### 1.3 Orphan записи и асоцииране

- Запис може да се създаде **без група** (orphan) — например нов контакт, който още не е свързан към досие.
- Падащ списък показва **само съществуващи** `id_gruppe` (и техните mutable `name_folder` етикети).
- При асоцииране към група записът става част от **всички профили** на тази група (защото всички профили споделят един и същ `id_gruppe`).
- След асоцииране се показват останалите автогенерирани профили с възможност за **премахване/пренасочване**.

### 1.4 Защо `id_gruppe` (а не `name_folder`) е в ключа

- `name_folder` е **потребителски етикет**, който може да се преименува.
- `id_gruppe` е **стабилен**, невидим за потребителя идентификатор.
- Ако ключът съдържаше `name_folder`, преименуване би **развалило** всички променливи. Затова в ключа влиза `id_gruppe`, а `name_folder` е просто display label.

## 2. Философия и принципи (от v3.0 — приети)

v3.0 остава **архитектурният гръбнак**. Приемаме я изцяло, но я подчиняваме на §1.

### 2.1 Осемте принципа (P1–P8)

1. **P1** Гъвкавост > фиксираност.
2. **P2** Всяко решение може да се смени през конфигурация, без рефакторинг.
3. **P3** Metadata-driven схеми (профилите са данни, не код).
4. **P4** Интерфейси, не конкретни имплементации (Repository, Storage, Renderer).
5. **P5** Събития за всичко наблюдаемо (Event Bus).
6. **P6** Версиониране на 4 нива (schema, API, data, UI).
7. **P7** Всяка промяна има миграция с rollback.
8. **P8** Всяко архитектурно решение се записва като ADR.

### 2.2 Шестте слоя (L1–L6)

```
L1 Config      config.yaml + schema registry
L2 Core        DI контейнер, EventBus, Registry, ключове/типове
L3 Domain      entities, use cases, правила за orphan/асоцииране
L4 Data        Repository interface → SQLite impl (днес), плъгини (утре)
L5 API         версиониран REST/интерфейс, legacy bridge
L6 UI          Admin панел + Cabinet + публични страници
```

### 2.3 Registry + metadata-driven

Един **Registry** държи всички дефиниции на профили, полета, типове и валидации. Нов профил = **запис в config.yaml** (или в БД), **не нов код**.

```yaml
profiles:
  "1001": # Служител
    label: { bg: "Служител", en: "Employee", de: "Mitarbeiter" }
    fields:
      - name: name
        type: string
        required: true
        indexed: true
      - name: egn
        type: string
        pattern: "^[0-9]{10}$"
        indexed: true
      - name: phone
        type: string
      - name: hired_at
        type: date
```

Това е **същото нещо** като променливата йерархия от §1, изразено гъвкаво: схемата казва **кои променливи съществуват** и **как се валидират**, а variable store държи **стойностите** им под композитния ключ.

## 3. Модел на данни (слят)

### 3.1 Хибриден модел

```
Релационен "индекс" (identity + links + полета с висока селективност)
        +
Variable store (стойности на всички полета под композитен ключ)
```

- **Релационната част** държи: `id_gruppe`, `name_folder`, `created_at`, връзки група↔запис, orphan статус, `audit_log`.
- **Variable store** държи стойностите на полетата. Полета, маркирани `indexed: true`, се **огледално държат** и в релационни колони (или SQLite FTS5/индекс) за бързо търсене — така решаваме риска "Performance загуби от JSON" от v3.0 §13.

### 3.2 Съпоставка с v4.x

| v4.x предлагаше      | v5.0 използва                         | Защо                         |
| -------------------- | ------------------------------------- | ---------------------------- |
| `data JSONB`         | variable store с композитен ключ      | запазва ядрото (§1)          |
| Свободна schema      | metadata-driven профилни схеми        | гъвкавост без загуба на тип  |
| Polyglot persistence | SQLite (днес) + Repository interface  | реалистично за add-on        |
| Event streaming      | Event Bus (in-process, днес)          | достатъчно за единичен add-on |

### 3.3 Таблици (SQLite, днес)

```sql
groups            (id_gruppe PK, name_folder, meta JSON, created_at)
profiles          (prefix PK, schema JSON, version)
records           (id PK, id_gruppe NULL, prefix, orphan INT, created_at)
variables         (key TEXT PK,        -- "{prefix}-{ID_db}-{id_gruppe}-{field}"
                   record_id, field, value_type, value_text, value_num, value_json,
                   updated_at)
links             (group_id, record_id)      -- асоцииране/премахване
audit_log         (запазва се от portal_enterprise)
```

`variables.key` е **каноничният** ключ от §1.1. `record_id` е обратна връзка за обновяване на отделен запис без да се парсва ключа.

## 4. Домейн модел (от v4.1 — орязан и заземен)

Bounded contexts от v4.1 остават полезни като **ментална карта**, но се реализират като **модули в един монолит**, а не като отделни услуги.

| Context       | Отговорност                                   | Реализация днес                     |
| ------------- | --------------------------------------------- | ----------------------------------- |
| Document      | досиета, профили, променливи, orphan          | ядрото §1                           |
| Identity      | потребители, права                           | scrypt + RBAC (от portal_enterprise)|
| Verification  | подпис/верификация, QR                       | hash-chain audit + signed URL       |
| Template      | шаблони 5000, генериране на PDF/OOXML         | съществуващ dependency-free writer  |
| Audit         | неизменяем журнал                            | hash-chain audit_log                |
| Workflow      | статуси на досие/документ                    | прости състояния (state machine)    |
| Tenant        | (само architecture-ready, вж. §5)            | —                                   |

**Правило:** един контекст = един модул с интерфейс. Не се създава microservice, докато add-on-ът е единичен процес.

## 5. Multi-Tenancy и Security (от v4.2/v4.3 — като „готовност", не като сегашна реализация)

v4.2 (Multi-Tenancy) и v4.3 (Zero Trust) са **ценни като бъдещ път**, но v3.0 §14 вече ги отложи. В v5.0 ги държим като **„architecture-ready"**:

### 5.1 Какво приемаме сега (евтино, висок ефект)

- **Security (непосредствено):**
  - scrypt + timing-safe сравнение (вече е в кода).
  - Argon2id при следващо докосване на auth (замяна на scrypt, ако е лесна).
  - AES-256-GCM за sensitive полета **по избор на поле** (променливите с `encrypted: true`).
  - RBAC + полево ABAC на ниво променлива (кой профил/поле кой може да чете/пише).
  - Rate limiting + signed URLs (вече е налице).
- **Multi-tenancy (само готовност):**
  - `tenant_id` като незадължителна колона/префикс в ключа, за да не се налага breaking change по-късно.
  - **Без** RLS-as-a-service, AsyncLocalStorage-per-request сървъри, квоти/биллинг, data-residency.

### 5.2 Какво отлагаме (v6.0+, само ако add-on-ът стане SaaS)

- OIDC/SAML/MFA/WebAuthn, OPA policy engine, HSM/Vault, mTLS/service mesh, SIEM/SOAR, ISO 27001/SOC 2/eIDAS сертификация, polyglot persistence, Kafka/event streaming, K8s.

Това не се изхвърля — стои в **Приложение B** като „път за мащабиране".

## 6. Какво строим СЕГА vs ПО-КЪСНО (заземен roadmap)

### 6.1 Фаза 1 — Ядрото (сега, в portal_enterprise)

1. **Registry + config.yaml** — дефиниции на профили 1000–5000 и техните полета.
2. **Variable store** — таблица `variables` с композитния ключ от §1.1.
3. **Автогенерация на профили** при създаване на група (папка).
4. **Orphan записи + асоцииране/премахване** (падащият списък само със съществуващи групи).
5. **Migration bridge** от текущите панели (§7).
6. **Admin UI** — показва йерархията: Група → Профили → Полета (това адресира „оскъдното извеждане" на информация).

### 6.2 Фаза 2 — Гъвкавост (рефакторинг към v3.0)

7. DI контейнер (< 100 реда) + EventBus.
8. Repository interface + SQLite имплементация.
9. Плъгини: storage, renderer (PDF/OOXML), OCR.
10. Версиониран API + legacy bridge (API v1 остава deprecated).

### 6.3 Фаза 3 — Полиране на документи/QR

11. QR per-file (не само per-portal) + legacy пренасочване.
12. Верификация на веригата (hash-chain) в UI, не само в логове.
13. Подпис + timestamp (SHA-256), PKCS#7 по-късно.

### 6.4 Отложено (v6.0+)

- Multi-tenancy реална, OIDC/MFA, HSM, service mesh, polyglot persistence — **само ако** продуктът напусне Home Assistant и стане SaaS.

## 7. Миграция от portal_enterprise v0.49

| portal_enterprise      | DOCFLOW v5.0                             |
| ---------------------- | ---------------------------------------- |
| `portals`              | `groups` + `records` (3000) + QR         |
| `files`                | `records` (2000) + storage               |
| `directory`            | `records` (1000)                         |
| `directory_variables`  | `variables` (variable store, ключ §1.1)  |
| `audit_log`            | `audit_log` (запазва се)                 |
| `settings.json`        | `config.yaml`                            |
| QR per-portal          | QR per-file + legacy mapping             |

**Стъпки:** Backup (db+files) → dry-run migration → real migration → verify integrity → switch → monitor. Всяка стъпка с rollback (< 5 мин).

## 8. Критерии за приемане (от v1.0, потвърдени)

1. Създаването на група автоматично генерира профилите 1000–5000.
2. Всяко поле се пази като променлива под `{prefix}-{ID_db}-{id_gruppe}-{field}`.
3. Преименуване на `name_folder` **не** разваля променливите (защото ключът е `id_gruppe`).
4. Orphan запис се създава без група и се асоциира по-късно; падащият списък показва само съществуващи групи.
5. Асоцииран запис става видим във всички профили на групата; премахване/пренасочване е възможно.
6. Търсене по `indexed: true` полета е бързо (индексирана колона/FTS5).
7. Админ панелът показва йерархията четливо (край на „оскъдното извеждане").

## 9. Консолидирани ADR (вместо 24 разпръснати)

| ADR    | Решение                                              |
| ------ | ---------------------------------------------------- |
| ADR-01 | Variable store с композитен ключ е ядрото (не JSONB) |
| ADR-02 | Metadata-driven профилни схеми (Registry)            |
| ADR-03 | Монолит с модули + интерфейси (без microservices)    |
| ADR-04 | SQLite + Repository interface (смяна по-късно)       |
| ADR-05 | `id_gruppe` стабилен, `name_folder` mutable label    |
| ADR-06 | Orphan-first, асоцииране по-късно                    |
| ADR-07 | `indexed:true` полета се държат и релационно         |
| ADR-08 | Версиониране: schema/API/data/UI                     |
| ADR-09 | Multi-tenancy и Zero Trust — architecture-ready      |
| ADR-10 | Всеки feature минава checklist-а на гъвкавост (§2.4) |

### 9.1 Checklist за гъвкавост (прилаган към всеки feature)

- [ ] Изключва се през config?
- [ ] Заменя се с алтернатива?
- [ ] Има интерфейс, не конкретна имплементация?
- [ ] Излъчва събитие?
- [ ] Има миграция с rollback?
- [ ] Документиран е в ADR?
- [ ] Тестван изолирано?

**Ако „не" на някое → не е готов.**

## 10. Отворени решения (към теб)

1. **Записът от v1.0**: `{prefix}-{ID_db}-{name_folder}-{field}` използваше `name_folder`. v5.0 го заменя с `{id_gruppe}` (ADR-05). Потвърждаваш ли?
2. **Порталният модел**: порталите остават `groups` + `records` (3000) с QR per-file — или порталът е отделно понятие извън профилната йерархия?
3. **Приоритет на Фаза 1**: започваме с ядрото (Registry + variable store + автогенерация + orphan/асоцииране) преди UI? Или първо довършваме UI редизайна, който вече е готов?
