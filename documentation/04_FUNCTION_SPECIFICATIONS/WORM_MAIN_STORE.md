# WORM за основното хранилище (F7-3)

Файл, който е влязъл в доказателство, не се презаписва. Кодът е в
`hapi_enterprise/worm.js`, тестът — `tests/worm.cjs`.

## Защо съществува

До 0.69.87 WORM имаше само **второто** копие: `mirror-target.js` пише с `Object Lock` в
режим `COMPLIANCE` и отказва триене. Основното хранилище
(`<DATA_DIR>/files/<portal>/<file>`) нямаше нищо — файл можеше да бъде презаписан на диска,
а манифестът на QR архива щеше да сочи към байтове, които вече не са същите. Това е точно
разликата между „пазим копие“ и „доказателството е проверимо“.

## Какво прави

1. Когато QR ревизия се архивира, `sealFiles` заключва всеки файл от манифеста с
   `chmod 0444` — само за четене за собственика, групата и останалите.
2. Оттам нататък `writeFile` без `unlink` пада с `EACCES`: презаписът е грешка, а не тиха
   подмяна.
3. `unseal` сваля защитата **съзнателно** — преди легитимна операция (изтриване на файл,
   нова версия, преместване). Иначе законна операция би се проваляла с неясна грешка.
4. `isSealed` чете **реалните права** от `stat`, не флаг в метаданните. Затова
   `integrity-scan` може да покаже `WRITABLE` — файл, който е доказателство, но е записваем.
   Това е находка, а не подробност.
5. `verify` приема списък и връща кои защитени файлове НЕ са само за четене.

## Границата, която се казва на глас

| Какво | Пази ли `worm.js` |
| ----- | ----------------- |
| Презаписване на байтовете | **да** — `EACCES` след `chmod 0444` |
| Изтриване на файла | **не** — собственикът на директорията пак може да го изтрие |
| Изменение от root | **не** — root не се спира от права |
| Windows | **частично** — `chmod` сменя бита „само за четене“ и `stat` го показва, но ОС не налага `EACCES` по същия начин |

Затова тук **не** се твърди „WORM като Object Lock“. Истинското неизменяемо съхранение иска
файлова система с append-only атрибут или външно хранилище с Object Lock — и точно това има
второто копие. Този модул затваря дупката „презапис без следа“, не цялата WORM тема.

Изтриването остава забранено по **друг** механизъм, който вече съществуваше:
`retention.protectionOf` връща причина (`sealed-flag`, `qr-manifest`, `qr-manifest-hash`,
`qr-manifest-version`, `archive-unindexed`) и `DELETE …/files/{fileId}` отговаря `409`.

## Кога се заключва

| Събитие | Какво се заключва |
| ------- | ----------------- |
| `POST …/qr/archive` (архивиране на QR ревизия) | всеки файл от манифеста на ревизията |
| `integrity-scan` | не заключва — само **проверява** и връща `WRITABLE` при разминаване |

## Одит

| Събитие | Кога |
| ------- | ---- |
| `worm.sealed` | след архивиране, с броя заключени файлове |
| `worm.seal.failed` | ако заключването не мине (липсващ файл, права) |
| `worm.verify.failed` | когато проверката намери записваемо доказателство |

## Какво НЕ е направено

- **Append-only атрибут на файловата система** (`chattr +a`) — не е преносим и не е наличен в
  контейнера на add-on-а.
- **Заключване на вече съществуващи архиви при обновяване** — файловете от стари архиви се
  заключват при следващото архивиране на съответния портал, не със скрипт за миграция. За
  инсталация, която иска всичко наведнъж, `integrity-scan` показва кои файлове са записваеми.
