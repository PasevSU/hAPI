# Опции на портала — `configuration.yaml`

> **Клас:** нормативен · **Собственик на факта:** договор на функция

Опциите на един портал живеят в ЕДИН файл в неговата папка. Този документ е договорът:
какво има във файла, кой го пише, как се чете и какво се отказва. Кодът е
`hapi_enterprise/portal-config.js` (договорът, без HTTP) и
`hapi_enterprise/routes/portal-config.js` (единственият HTTP вход); папката се обслужва от
`hapi_enterprise/portal-folder.js`.

## Защо съществува

До 0.69.233 опциите на портала бяха разпръснати в четири места, които не се знаеха едно за
друго: базата (`visibility`, `access`, `folderMeta`), файловете в базата (`accessMode`),
глобалните настройки (`requirePortalToken`, лимити) и опциите на add-on-а (44). Последиците:

1. папката не се самодокументира — човек през Samba не разбира защо една папка е скрита;
2. копиране на папката в друга инсталация връща файловете, но не и опциите;
3. две истини за едно и също (`folderMeta` и `folderNotes` в различни полета);
4. никой не проверява, че избраното е приложено.

Затова описанието е файл в САМАТА папка на портала. Базата остава това, което сървърът чете
бързо, но за опциите се смята за огледало на файла.

## Място и име

```
<логически корен>/hAPI/portals/<slug>/configuration.yaml
```

- **Само в корена на портала.** В подпапките няма `configuration.yaml` — флаговете им се пазят
  в същия файл, в секцията `folders`.
- **Един файл на портал.** Съществува ВИНАГИ, когато съществува папката на портала: файл без
  папка няма къде да стои.
- Пътят се строи само през `paths.js` (`paths.portalsRoot()` / `portalRootFor()`); модул не
  строи `<диск>:\share` сам.
- Файлът **не е съдържание**: не се показва в дървото на портала, не влиза в `files[]`, не се
  брои за качен файл.

### Кога се появява файлът

`storage_root` на портала е собствен път (`/share/hAPI/portals/<slug>`) от 0.69.234, но
САМАТА папка се създава при първа нужда. Затова файлът се появява заедно с папката, по един от
тези пъти:

| Път | Кога |
| --- | --- |
| създаване на портал / старт на add-on-а | при `portal_folder_copy: true` — папката и файлът се създават заедно |
| качване на файл в портала | при `portal_folder_copy: true` (`portalFolder.store()` → `ensure()`) |
| нова папка от панела | винаги — създаването на която и да е папка в портала създава и корена, а с него и описанието |
| първи запис през `PUT …/config` | винаги — записът създава папката, ако я няма |

Дотогава `GET …/config` връща `exists: false` с готовия шаблон (`data`), тоест панелът вижда
опциите, преди файлът да е на диска. `portal_folder_copy: false` е изричното решение „не
създавай папка на портала, докато човекът не поиска“ — то не забранява описанието, а отлага
папката.

## Формат: плосък списък, не дървета

Опциите стоят на едно ниво (`visibility`, `access_mode`, `ui_columns`), не в групи
`portal:`/`access:`/`qr:` — така всяка опция се намира с търсене и се включва/изключва сама.

```yaml
version: 1
revision: 7
updated_at: "2026-11-17T08:00:00Z"
id: dogovor-lichni-dokumenti-001
slug: dogovor
name: Лични документи
visibility: private
flag: none
category: ""
subject: ""
notes: ""
contact_id: ""
case_id: ""
parent_id: ""
readonly: false
access_mode: key
access_review_only: false
access_download_requires_key: true
temporary_default_ttl: 24h
temporary_default_read_only: true
temporary_password_required: false
qr_style: frame
qr_caption: url
qr_levels_folder: true
qr_levels_file: true
qr_archive_on_change: false
folders_default_visible: true
folders_default_media: false
folders_default_locked: false
storage_subpath: ""
storage_copy_to_folder: true
ui_columns: 3
ui_show_sizes: true
audit_telemetry: true
off: []
folders:
  "/Договори":
    visible: false
    media: true
    locked: true
    reason: лични данни
files:
  - id: file-000001
    path: /dokument.pdf
    size: 1024
    sha256: "0f1e…"
    access: key
    listed: true
```

Правила, които се пазят от тестове:

| Правило | Защо |
| --- | --- |
| **Всяка опция присъства винаги** | липсващ ключ не е „подразбиране“: тогава файлът не казва какво се прилага. Отсъствието е грешка с име на опцията |
| **`off: []` изключва без загуба** | стойността остава за връщане; изключването е отделен флаг, не изтриване на ред |
| **Детерминиран запис** | фиксиран ред на ключовете; `files[]` подреден по `path` → един и същ набор дава един и същ текст, diff-ът е четим |
| **Само UTF-8, LF** | един CRLF чупи проверките на дървото и `build-release` |
| **Без тайни** | никакви токени, пароли или ключове — те остават в базата/`secrets.yaml` |

Подмножеството на YAML е съзнателно ограничено (нула runtime зависимости): обекти до 4 нива,
скалари, bool, числа, списъци от скалари и списък от обекти с фиксиран ред на ключовете, плюс
коментари. Забранени: табулация за отстъп, дублиран ключ, anchors/aliases, многоредови блокове,
изрази, голи стойности с `:` или `#`. Непознато нещо се ОТКАЗВА с ред, а не се прескача —
тихото прескачане е начинът една опция да изчезне, без някой да разбере.

## Идентификатор: `{{portal}}-{{portal_name}}-001`

| Част | Какво е | Пример |
| --- | --- | --- |
| `{{portal}}` | стабилният ключ на портала (slug) | `dogovor` |
| `{{portal_name}}` | името в машинен вид — кирилица → латиница, интервали → едно тире | `lichni-dokumenti` |
| `-001` | пореден номер, ТОЧНО три цифри | `-001` |

- Идентификаторът се издава веднъж и не се сменя при смяна на заглавието.
- Номерът гледа **издадените**, не броя: изтрит обект оставя празнина и не освобождава ред.
- Две части или четири цифри е невалиден идентификатор — отказ с име на полето.

## Опции

Редът е и редът във файла. Колоната „тип“ е това, което проверката приема.

| Опция | Тип | По подразбиране | Ограничение |
| --- | --- | --- | --- |
| `slug` | низ | — | `^[a-z0-9][a-z0-9-]{1,62}$`, съвпада с името на папката |
| `name` | низ | — | 1–160 знака (заглавие на портала) |
| `visibility` | enum | `private` | `public` \| `private` |
| `flag` | низ | `none` | до 64 знака |
| `category` | низ | `""` | до 120 знака |
| `subject` | низ | `""` | до 200 знака |
| `notes` | низ | `""` | до 2000 знака |
| `contact_id` | низ (ид.) | `""` | букви, цифри, `-`, `_` |
| `case_id` | низ (ид.) | `""` | същото |
| `parent_id` | низ (ид.) | `""` | същото |
| `readonly` | bool | `false` | `true` само за спътника „само за четене“ |
| `access_mode` | enum | следва видимостта | `""` \| `free` \| `key` \| `token` |
| `access_review_only` | bool | `false` | — |
| `access_download_requires_key` | bool | `true` | — |
| `temporary_default_ttl` | enum | `24h` | `1h` \| `6h` \| `24h` |
| `temporary_default_read_only` | bool | `true` | — |
| `temporary_password_required` | bool | `false` | — |
| `qr_style` | enum | `frame` | `frame` \| `plain` |
| `qr_caption` | enum | `url` | `url` \| `title` |
| `qr_levels_folder` | bool | `true` | — |
| `qr_levels_file` | bool | `true` | — |
| `qr_archive_on_change` | bool | `false` | — |
| `folders_default_visible` | bool | `true` | — |
| `folders_default_media` | bool | `false` | — |
| `folders_default_locked` | bool | `false` | — |
| `storage_subpath` | низ | `""` | празно или относителен път ≤ 3 сегмента, без `..` |
| `storage_copy_to_folder` | bool | `true` | — |
| `ui_columns` | enum | `3` | `2` \| `3` \| `4` |
| `ui_show_sizes` | bool | `true` | — |
| `audit_telemetry` | bool | `true` | — |

Две неща НЕ са опции, а данни:

- **`folders`** — флаговете по път (`visible`/`media`/`locked`/`reason`). Заключена папка без
  `reason` (1–500 знака) се отказва: заключването е твърдение за човека отвън и без основание
  не може да бъде проверено по-късно. Пази се само ИЗКЛЮЧЕНИЕТО от подразбирането.
- **`files[]`** — географията на портала: кой файл къде е. Полета: `id`, `path`, `size`,
  `sha256`, `version`, `access`, `listed`, `mirror`, `added`, `modified`, `content_id`.
  `path` е уникален БЕЗ значение от регистъра (на NTFS `A.pdf` и `a.pdf` са един файл);
  забранени имена: `configuration.yaml`, `portal.html`, `api.json`, `openapi.json`, `.worm` и
  всичко започващо с `.`.

## Посока на истината

| Събитие | Какво се случва |
| --- | --- |
| папката на портала се появи (вж. таблицата горе) | файлът се създава с шаблона + самоличността от портала (`slug`, `name`, `visibility`, флаг, тема) |
| качване/триене/местене/възстановяване | `files[]` и самоличността се сглобяват наново от ЗАПИСА; настройките от човек оцеляват |
| промяна от панела (`PATCH /admin/api/portals/{id}`) | стига до файла през `writeApiDir` → `syncConfig` |
| запис през `/config` (`PUT`/`import`) | опциите влизат в записа (`config.adopt`), а файлът се сглобява наново от записа |
| ръчна промяна във файла (Samba/редактор) | вижда се при следващото четене; в базата влиза само с `POST …/config/adopt` |
| счупен файл | НЕ се презаписва. Качването в портала продължава да работи — чужда работа не се губи заради чужда грешка |

`revision` расте САМО при истинска промяна на съдържанието (сравнение без `revision` и
`updated_at`). Иначе всяка заявка щеше да „вдига ревизия“ и чекпойнтът в панела щеше да стане
безсмислен.

## HTTP договор

Всички пътища са под `/admin` и изискват административна идентичност. Правото е `portals`
(admin и operator — пълно; viewer — само четене, тоест `GET`).

| Метод | Път | Какво прави |
| --- | --- | --- |
| `GET` | `/admin/api/portals/{id}/config` | `{ file, exists, hash, revision, legacy, data, effective, problems }`. Не пише файл |
| `PUT` | `/admin/api/portals/{id}/config` | запис на промяната; чекпойнт в `expectHash` (тяло) или `If-Match` (заглавка) |
| `POST` | `/admin/api/portals/{id}/config/verify` | `{ ok, missing[], extra[], changed[], unreadable[], hash, revision, checked }` — сверка с диска |
| `POST` | `/admin/api/portals/{id}/config/adopt` | внася текущите стойности от файла в записа (одит `portal.config.adopt`) |
| `GET` | `/admin/api/portals/{id}/config/export.yaml` | файлът както е на диска (`application/yaml`, `no-store`, `ETag`, `X-Config-Hash`) |
| `POST` | `/admin/api/portals/{id}/config/import` | цял YAML заменя описанието; `?dry=1` връща само разликата |

Отговори при отказ:

| Случай | Код | Тяло |
| --- | --- | --- |
| запис върху чужда промяна | `409` | `{ error: PORTAL_CONFIG_CONFLICT, currentHash, diff[] }` |
| липсва чекпойнт при съществуващ файл | `409` | същото, с `currentHash` |
| липсва чекпойнт изобщо | `400` | `PORTAL_CONFIG_HASH_REQUIRED` |
| описание не минава проверката | `422` | `{ error: PORTAL_CONFIG_INVALID, issues: [{ path, line, message }] }` |
| порталът ползва общ корен (няма своя папка) | `409` | `PORTAL_CONFIG_NO_FOLDER` |
| файлът още не съществува (за `verify`/`adopt`/`export`) | `404` | `PORTAL_CONFIG_MISSING` |

`verify` отчита `extra` за файл, добавен НАПРАВО в папката. Той съзнателно НЕ влиза в
`files[]` сам: регистрирането на чуждо съдържание без избран режим на достъп би дало на портала
файл, за който никой не е решил дали се вижда.

## Какво вижда панелът

Блокът „Опции“ в контролния панел показва ЕФЕКТИВНИТЕ стойности (не само записаните) в четири
раздела — Портал · Достъп · QR · Интерфейс — плюс:

- чекпойнта (`hash`) като текст;
- „Провери папката“ — същият `verify`;
- „Покажи файла“ — самият файл през `export.yaml`, не сглобен от панела.

Записът минава през `PUT` с чекпойнта от последното четене. При `409` панелът НЕ презаписва на
сляпо: презарежда файла и казва, че нещо друго го е променило.

## Кодове и одит

Кодове: `PORTAL_CONFIG_INVALID`, `PORTAL_CONFIG_CONFLICT`, `PORTAL_CONFIG_HASH_REQUIRED`,
`PORTAL_CONFIG_MISSING`, `PORTAL_CONFIG_NO_FOLDER`, `PORTAL_CONFIG_UNREADABLE`.

Одит: `portal.config.read`, `portal.config.verify`, `portal.config.adopt`. Всяка мутация през
`PUT`/`import` също минава през `portal.config.adopt`, защото внася опциите в записа.

## Обратна съвместимост

До 0.69.235 файлът беше с групи `portal:`/`access:`/`qr:`. Такъв файл се разпознава
(`legacy: true`), превежда се при ЧЕТЕНЕ и се записва в плоския вид при първия запис. Липсващите
тогава опции се допълват от подразбиранията, а идентичността се издава веднъж. Затова никой
съществуващ портал не остава без описание заради смяна на формата.

## Правило, което не се разхлабва

Описанието се чете и пише САМО през `portal-config.js`, а HTTP входът е САМО
`routes/portal-config.js`. Втори четец на YAML, втори начин за смятане на `sha256` (вместо
`core.api.hash.digest`) или втори запис на файла (извън `write()`) е регресия.

Общите форми (`SLUG`, `SHA256`, `FILE_ID`, `CONTENT_ID`, `ID_FIELD`, `ISO`) живеят на едно място
(`portal-config.RULES`) и `portal-folder.js` ги взима оттам — два комплекта проверки на едно и
също не бива да съществуват.

## Дневник на проверките

Проверка, която не оставя ред в дневника, не се ЗАСИЧА. Затова всяка проверка от панела минава
през `check-log.js` и се пише като `check.<име>` с `ns: 'check'`:

| Име | Къде се вдига | Какво мери |
| --- | --- | --- |
| `check.integrity` | `GET …/integrity` | сверка на `files[]` с диска, брой файлове и време |
| `check.integrity-job` | фоновата задача | същото, но по разписание и с `jobId` |
| `check.qr` | `routes/portal-qr.js` | архив · сверка · възстановяване · прекратяване |
| `check.token` | `routes/portal-tokens.js` | издаден токен, `maxUses`, срок |
| `check.config` | `routes/portal-config.js` | сверка на описанието с диска |
| `check.key` | завъртане на ключа за подпис | нов ключ, отпечатък |

Договорът е тесен и без състояние: `start` (info) → `ok` (info) · `fail` (warn) · `crash` (error).
`fail` и `crash` влизат и в централизирания журнал на грешките (`GET /admin/api/errors`), защото
успешните проверки не носят информация на онзи, който търси проблема; `ok` остава само в общия
дневник. `crash` е отделен от `fail` нарочно: счупена проверка не е „проблем във файловете“, а
дефект, който иначе изчезва в `500` без следа. Нищо в дневника не хвърля — наблюдаемостта не бива
да събаря проверката.

Списъкът с имена е ЗАТВОРЕН (`check-log.NAMES`). Име извън него се пише като `check.unknown`, за
да се види, че някой е подал име извън договора, вместо редът да пропадне безследно.

Присъдата „мина ли“ се смята на ЕДНО място — `verify-verdict.js`. Обобщението на сверката брои
по статус (`VERIFIED`, `MISMATCH`, `MISSING`, `INVALID_TYPE`, `ERROR`, `WRITABLE`), а не връща
поле `failed`; затова `MISMATCH`/`MISSING`/`INVALID_TYPE`/`ERROR` са провал, а `WRITABLE` е
предупреждение (файлът е сменяем, което не доказва подмяна). Панелът, синхронният вход и
фоновата задача ползват същата функция, защото досега панелът четеше `summary.mismatch` с малки
букви и показваше „разминават се 0“ точно при подмяна.

## Функции на портала

Функциите на портала са ЕДИН обект (`FUNCTIONS` в `ui/portal-control.js`), а не бутони, разпръснати
по блокове. Всеки ред носи `id`, област, ключ за име, икона от йерархията на спрайт v4
(`ui/icons-v4-map.json`) и резервна икона от вграденото множество, ако спрайтът не се зареди.
Панелът рисува редовете от този списък, а `ui/files-manager.js` вързва изпълнение по СЪЩИЯ `id`.

| Част на реда | Значение |
| --- | --- |
| чекбокс `[data-fn-check]` | включва функцията в „Изпълни избраните“ |
| `[data-fn-state]` | състояние с икона: `loading` · `success` · `failure` (не само с цвят) |
| бутонът (старият `id` без `pf-`) | изпълнява САМО тази функция, както досега |
| `#pf-fn-run` | общо изпълнение по реда на екрана, с брояч на отметнатите |

Правила: бутонът НЕ стои в `<label>`, иначе щракването му би отметнало чекбокса; ред без вързан
обработчик се показва ЗАБРАНЕН, а не мъртъв; грешка в една функция не спира останалите и накрая се
казва „минали N от M“; състоянието се маркира с икона, за да не зависи от различаване на цветове.
Текстовете на обекта са ключове `pc.fn.*` на трите езика — в модула няма нито един ръкописен низ.

## Тестове

| Тест | Какво пази |
| --- | --- |
| `portal-config-format` | обратен прочит байт по байт, откази (табулация, дублиран ключ, кавички, anchor), плоският вид |
| `portal-config-ids` | трите части на идентификатора, транслитерация, номер без преизползване, `off:`, превод на стар файл |
| `portal-config-files` | `files[]`: ред по път, уникален `id`/път без регистър, забранени имена, сверка |
| `portal-config-registry` | атомарен запис, `revision` 1→2, чекпойнт с `hash` и `diff`, регистър на папките |
| `portal-config-seed` | файлът е в папката, ръчна промяна оцелява, не се брои за съдържание |
| `portal-config-sync` | качване/триене обновяват `files[]`; празна промяна не вдига ревизия; счупено не се презаписва |
| `portal-config-template` | файл при създаването, пълнота срещу шаблона, `PATCH` → файл, възстановяване от шаблона |
| `portal-config-api` | маршрутите: чекпойнт, `409`/`422`, `verify`, `import` (`dry`), `adopt`, `export.yaml` |
| `portal-config-ui` | блокът „Опции“: четири раздела, запис, проверка, разпечатка |
| `check-log` | договорът на дневника: четирите изхода, затвореният списък, `check.unknown` |
| `check-log-integration` | проверките стигат до дневника и до журнала на грешките, включително присъдата |
| `verify-verdict` | кои статуси са провал и кои само предупреждение |
| `ui-portal-functions` | обектът на функциите: икони в йерархията, чекбокс, състояние, общо изпълнение |
