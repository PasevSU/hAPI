# Ежедневни операции — обновяване, образ, секрети

Три неща, които се правят след всяко издание, и трите имат скрипт, за да не се правят на ръка.

## 1. Обновяване на add-on-а

```bash
ha store reload
ha apps update 99438e72_hapi_enterprise
```

От 0.69.154 насам `config.yaml` има `image:`, тоест store-ът **тегли** готов образ вместо да
го строи на машината. Измерено на Raspberry Pi 4: **129 s build → 14 s pull** за същия Upgrade.
Ако някога образът липсва за дадена архитектура, Supervisor пада с грешка при теглене — затова
преди всяко издание се проверява, че образът е публичен:

```powershell
pwsh -File scripts/check-addon-image.ps1 -Version 0.69.163
#   OK   ghcr.io/pasevsu/amd64-addon-hapi_enterprise:0.69.163 · HTTP 200
#   OK   ghcr.io/pasevsu/aarch64-addon-hapi_enterprise:0.69.163 · HTTP 200
```

Два реда, не три: от 0.69.163 `arch` е само `amd64` + `aarch64` — Supervisor пази
`armv7`/`armhf`/`i386` в `ARCH_DEPRECATED` и 32-bit HAOS вече не се публикува.

Скриптът пита **registry API-то** (`https://ghcr.io/v2/<owner>/<repo>/manifests/<tag>`) с
анонимна заявка — точно това прави Supervisor. Две грешки, които вече са поправени и не бива
да се връщат: адрес без `/v2/` е страница на сайта (404 върху съществуващ образ), а `Accept`
само за multi-arch index не приема обикновен манифест.

## 2. Обновяване на интеграцията (без HACS)

```powershell
pwsh -File scripts/update-integration.ps1                               # само проверка какво ще се сложи
pwsh -File scripts/update-integration.ps1 -Execute -HaHost 192.168.50.4  # в /config/custom_components на HA
```

Скриптът сваля `hapi_enterprise-integration-<версия>.zip` от последното издание, качва го и
**разменя папката атомарно**: новото се разархивира в `/tmp`, старият вариант се мести на
`hapi_enterprise.bak`, новият заема мястото му и едва тогава `.bak` се трие. При провал старият
вариант се връща на мястото си — Home Assistant не остава без интеграция. Рестартът на HA не е
част от скрипта: той е решение на човека.

При `-HaHost` версията „на място“ се пита **на самия HA**, а не на локалния диск (иначе
`Test-Path /config/...` на Windows винаги казва „няма“).

## 3. Одит на `secrets.yaml`

```powershell
pwsh -File scripts/audit-ha-secrets.ps1 -HaHost 192.168.50.4
```

Показва за всеки ключ: **име, форма, дължина и кой YAML го ползва** — и никога стойността.
Формите, които разпознава: HA long-lived token, GitHub PAT / fine-grained, AWS ключ, `sk-…`,
Slack, частен ключ, обикновен низ.

Защо така: четенето на файла „на ръка“ изкарва живите ключове в конзолата, в логовете и в
историята на чата. Този скрипт съществува, за да не се случва това.

Изходът завършва с два списъка:

- **чувствителни и непотребявани** ключове — махат се от файла и се **отзовават** при
  доставчика (GitHub: https://github.com/settings/tokens);
- напомняне, ако в `secrets.yaml` има HA long-lived token — виж `admin-token.md` защо не бива
  да е и токенът на hAPI.

Закоментираните редове (`# !secret …`) не се броят за употреба — иначе одитът лъже, че всичко
се ползва. На HA `grep` е BusyBox и не познава `--include`, затова скриптът минава с цикъл по
файловете.

## 4. Ротация на администраторския токен на hAPI

1. Генерирай случаен низ, 32+ знака (не преизползвай стар ключ и не ползвай HA LLAT).
2. Настройки → Add-ons → hAPI Enterprise → **Конфигурация** → `token` → новия низ → Запази.
   Add-on-ът се рестартира; CLI `ha` **няма** команда за опции, затова това е UI стъпка.
3. Обнови клиентите на hAPI (портал, скриптове, автоматизации) с новия токен.
4. Ако старият е бил HA long-lived token — **отзови го** в Профил → Сигурност → Long-lived
   access tokens.
