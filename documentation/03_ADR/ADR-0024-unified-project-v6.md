# ADR-0024: Обединяване на всички идеи в един проект (v6.0)

- **Status:** Accepted
- **Дата:** 2026-10-20

## Контекст

Проектът има дълга история в няколко паралелни места:

- текущото репо (`hapi_enterprise/`, v0.50.0) с `docs/plan/00…14` и `documentation/` (00–08);
- worktree `hAPI Enterptice.worktrees/pr/3-dependabot`;
- `hapi_old/hAPI_enterprice` (v0.43-rc7) — build скриптове, brand kit, 8 UI макета;
- `hapi_old/hAPI_Enterptice_v0.47_snapshot` — първи SDK клиент, desktop UI, GUI панели;
- `hapi_old/HAPI.SU` (v0.49.1) — критичен анализ, стар HA мост, ~40 release архива;
- `hapi_old/doku/plan` — планове v1.0–v4.3;
- външна тема „Създаване на публично API“ (ChatGPT), чиито идеи вече частично
  съществуват в кода (`/api/v1/p/{slug}`, `openapi.json`, `api-version.js`, HA мост).

Резултатът: **няколко документа задават различен roadmap**, стари идеи се губят, а
публичното API съществува без договор и без SDK. Това прави приоритизацията и
release gate-а нееднозначни.

## Решение

1. **Един каноничен документ** — `docs/plan/15-unified-master-plan-v6.0.md`. Той задава
   обхват, фази (0–10) и backlog с ID-та; `08`–`14` остават като история и детайлни
   приложения.
2. **Правило за решения** — всяка идея получава `KEEP` / `MERGE` / `DROP` / `DEFER`
   с източник и фаза (трассируемост §9 в плана).
3. **Нови фази:**
   - **8 — Публично API v2 + SDK**: контракт-първо (`api/openapi.yaml`), четири класа
     идентичности (порталeн ключ, файлов ключ, service токен с обхвати, PKCE/OIDC),
     `problem+json`, `ETag`, `Idempotency-Key`, `429` по токен, webhooks, `sdk/js`.
   - **9 — Пакетиране и доставка**: един build → 6 пакета, Windows runtime, brand kit.
   - **10 — Качество и CI**: всички 11 препоръки от `HAPI.SU/ANALYSIS.md` като `BUG-*`.
4. **Физическа консолидация** — целева структура с `api/`, `sdk/js/`, `archive/`,
   `docs/api/`; бинарните архиви и `node.exe` **не** влизат в git.
5. **Забрани** (от историята): не се връщаме към `data JSONB`, microservices,
   PostgreSQL/Kafka/K8s/HSM като текуща архитектура; без feature без backend handler и
   тест; без `ADMIN_TOKEN` на публични повърхности.

## Последици

**Плюс**
- Един roadmap и един backlog → ясна приоритизация и release gate.
- Публичното API става продукт с договор, SDK и тестове (Фаза 8).
- Старите идеи не се губят: всяка има ред в трассируемостта с решение.
- Репото остава малко (без 660 MB архиви), а историята е достъпна през `archive/`.

**Минус / рискове**
- Фаза 8 добавя обхват; смекчаване: тя надгражда вече съществуващи маршрути и
  `sdk/client.mjs`, не нов backend.
- `server.js`/`admin.js` остават монолитни до Фаза 10 — документиран дълг (`BUG-08`).
- Съдържанието на външната ChatGPT тема не е четено (частен линк); §12 в плана
  предвижда сверка, ако бъде предоставено.

## Алтернативи

| Алтернатива | Защо не |
| --- | --- |
| Да остане v5.0 като каноничен | Не покрива публично API, пакетиране и CI; губи стари идеи |
| Да се обедини чрез ново репо | Скъпо, чупи историята и тестовете (76 файла) |
| Да се пренесе целият `hapi_old` в git | 660+ MB бинарни архиви, дублиран код |
| Да се изчака Фаза 7 преди Фаза 8 | Публичното API е нужно и на Фаза 7 (verify/chain endpoint-и) |
