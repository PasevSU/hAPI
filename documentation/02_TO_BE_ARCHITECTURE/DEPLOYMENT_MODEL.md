# Модел на внедряване — add-on или Docker Compose

Отговор на въпроса: **hAPI да работи като Home Assistant add-on, или като самостоятелен
Docker Compose стек, към който HA се свързва?**

Кратък отговор: **add-on-ът остава основният и единствен поддържан режим за HA потребители.
Compose се добавя като втори режим само с два контейнера (`hapi` + по избор `minio`), и то
когато има реален потребител извън HA. PostgreSQL, Redis и отделен worker не влизат.**

Вид: **преглед със решение**. Нормативните правила са в `SECURITY_MODEL.md`,
`STORAGE_ARCHITECTURE.md` и `API_ARCHITECTURE_SPEC.md`; този документ само казва къде се
изпълняват.

## 1. Какво е hAPI днес (измерено, не предположено)

| Факт | Стойност | Откъде |
| --- | --- | --- |
| Един контейнер | `node:22.21.1-alpine3.23`, `CMD node /app/start.js` | `hapi_enterprise/Dockerfile` |
| База | `node:sqlite` (вградена в Node), WAL, `synchronous=FULL` | `sqlite-store.js:5,12` |
| Резервно копие | `backup: cold` — Supervisor спира add-on-а за snapshot | `config.yaml` |
| Runtime зависимости | **нула** (`dependencies` липсва в `package.json`) | `package.json` |
| Входове | ingress 8098, вътрешен API 8099, Public Gateway 8088 | `config.yaml` |
| Опашка | собствена, persistent FIFO с пауза/възобновяване и възстановяване след crash | `job-manager.js` |
| Заключване | `instance-lock.js` (един екземпляр) | — |

Тези седем реда са причината отговорът да не е „да, давайте пет услуги“.

## 2. По услуга — защо да или защо не

### 2.1 PostgreSQL — не сега

- **Техническата причина е една и е твърда:** Node няма вградена PostgreSQL връзка.
  `node:sqlite` е built-in, Postgres не е. Внасянето му значи първата **runtime** npm
  зависимост (`pg`) — тоест `npm install` в образа, който точно днес изчистихме от npm и от
  неговите CVEs (0.69.87), плюс `npm audit` в release цикъла завинаги.
- **Преносимите части не са малки:** `sqlite-store.js` + `sqlite-repository.js` + миграциите +
  тестовете, които четат базата директно. Това не е „смяна на connection string“.
- **Резервното копие се чупи.** Днес студеният snapshot на Supervisor взима един файл. С
  Postgres в страничен контейнер snapshot-ът на add-on-а вече не е консистентен и трябва
  отделен `pg_dump` цикъл — тоест нова експлоатационна отговорност.
- **Какво трябва да е вярно, за да влезе:** няколко едновременни писача, метаданни, които не
  се побират в един файл, или изискване за клъстер. Днес нито едно от трите не е измерено.

### 2.2 Redis — не сега

- Същата твърда причина: няма вградена Redis връзка в Node → пак npm зависимост.
- **Няма какво да опашка.** `job-manager.js` вече е persistent FIFO с ограничение, пауза,
  възобновяване и маркиране на `interrupted` след рестарт. Redis би добавил стойност само при
  няколко процеса, които делят една опашка — а add-on-ът е един процес.
- **Какво трябва да е вярно, за да влезе:** втори `hapi` процес. Тогава първият проблем не е
  опашката, а `instance-lock.js` и SQLite писачите.

### 2.3 MinIO — да, но като втори backend на съществуващото огледало

- S3 е HTTPS + SigV4, а подписът се прави с `node:crypto` и `fetch` — и двете вградени. Това е
  **единствената** от трите услуги, която не чупи правилото за нула зависимости.
- Тя не добавя ново поведение, а **нов вид цел** за поведение, което вече работи (виж §3).

### 2.4 Отделен `hapi-worker` — не

Два процеса върху една SQLite база е по-лошо от един: два писача, един `instance-lock.js`,
двойна семантика на опашката. `job-manager.js` вече възстановява задачи след crash в рамките на
процеса. Отделен worker има смисъл само след като Postgres е факт — тоест след като предпоставката
му е изпълнена, а тя е отхвърлена в §2.1.

## 3. Огледалото вече съществува — липсва само целта

Това е най-важният ред в документа. „M1 огледало“ от `READY_MADE_COMPONENTS.md` е **наполовина
готово в продукционен код**:

| Какво | Къде |
| --- | --- |
| Опция `storage_mirror` (второ копие на всеки файл) | `config.yaml`, `start.js` |
| Запис с `flag:'wx'`, права `0600`, после **прочитане и сравнение на `sha256`** | `server.js` → `storeMirrored()` |
| При разлика: файлът се трие, одит `file.mirror.failed` | същото място |
| Самолекуване при четене: липсващ оригинал се връща от копието, одит `file.mirror.restored` | `readPlainBuffer()` |
| Проверка и поправка по заявка | endpoint за verify/repair на огледалото |
| Сензор за провали | `mirror_failures` в `decision-sensors.js` |
| Ограничение: целта трябва да е в `/share`, `/media` или `/config` | `server.js` (или `STORAGE_MIRROR_ANY`) |

Липсва точно едно нещо: **целта е папка, а не кофа.** Затова честната малка стъпка не е
compose стек, а втори вид цел (`path` \| `s3`) зад същия договор: записва се два пъти,
проверява се, поправя се, одитира се, брои се в същия сензор.

Това е и отговорът на възражението „Docker няма да реализира нашите договори“: вярно е, и
затова не му ги даваме. Object Lock пази байтовете; кой файл е бил публикуван под кой QR
продължава да казва нашият манифест.

## 4. Решението

| Въпрос | Решение |
| --- | --- |
| Основен режим | **HA add-on** — един контейнер, ingress, `backup: cold`, нула зависимости |
| Втори режим | **Docker Compose** — само `hapi` + bind mount за `/share`; `minio` по избор |
| PostgreSQL / Redis / worker | **не влизат** — предпоставките им не са изпълнени и всяка чупи нулата зависимости |
| Кой режим е „истинският“ | и двата, но **нито една функция не бива да работи само в единия** |
| Object Lock | влиза като втора цел на огледалото, не като нов слой в архитектурата |

### 4.1 Ако се добави Compose, правилата са

- същите имена на настройки като add-on-а (`STORAGE_MIRROR`, `PUBLIC_BASE_URL`, …) — един код,
  два входа, без „в compose се прави другояче“;
- `/share` е bind mount, не volume с друга структура;
- `restart: unless-stopped`, `healthcheck` към `/health`, без `privileged`, без root;
- `minio` е **по избор**: `hapi` стартира и работи без него, както днес работи без
  `storage_mirror`;
- compose не носи своя версия и не се публикува като отделен артефакт — той е вход към същия
  образ от `dist/`.

### 4.2 Цената, която се плаща

- втори начин да се счупи и втори набор документация;
- `verify-release` не покрива compose — трябват 2–3 проверки в матрицата (важи ли образът,
  стартира ли без `minio`, същите ли са пътищата);
- поддръжка на два режима от един човек.

Ако цената не е приемлива, правилното решение е **само add-on**, а MinIO се добавя като
външна услуга, конфигурирана с адрес — без compose в хранилището.

## 5. Следваща стъпка

1. **Първо втората цел на огледалото** (`path` \| `s3`), защото тя носи ползата и в двата
   режима и не изисква нито една нова услуга. **Готово в 0.69.87** (`mirror-target.js`:
   `s3://bucket/prefix?endpoint=…&lock=дни`, SigV4 с `node:crypto`, Object Lock COMPLIANCE;
   тестове `mirror-target` и `mirror-s3-wiring`).
2. **Правилото в `retention.js`** — `EVIDENCE`-клас файл никога не се трие. Без него Object
   Lock и retention си противоречат (виж `READY_MADE_COMPONENTS.md` §2.4). **Готово в 0.69.87**
   (`EVIDENCE_NEVER_DELETED`, `tests/retention-evidence.cjs`).
3. **Compose — само при поискване.** Дотогава add-on-ът е истината и няма втори режим, който
   да се разминава с него.

Бележка за версията: предложението цитира `v0.69.73`; текущата версия в хранилището е
**0.69.87**. Моделът на внедряване не променя номера на версията — той се вдига само при
издание.
