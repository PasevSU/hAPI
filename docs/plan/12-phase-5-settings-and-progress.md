# DOCFLOW — Фаза 5: Настройки (функции) + информационен блок за прогрес/статус

> **Статус:** Работен план (за изграждане). Продължава завършените Фази 1–4.
> **Базов документ:** `08-master-plan-v5.0.md` §2 (L1 Config, L5 API, L6 UI) и `09-execution-plan.md`.
> **Цел:** Настройките да са видими, обяснени и безопасно редактируеми; всяка дълга
> операция да показва прогрес и краен резултат (успех/провал) без да се губи контекст.

---

## 1. Защо (мотивация)

Две оплаквания от реалната употреба:

1. **„Извеждането на информация е изключително оскъдно“** — настройките съществуват в
   backend (`runtime-config.js`), но в UI не са групирани, обяснени и валидирани на
   място; потребителят не вижда кое веднага влиза в сила и кое изисква рестарт.
2. **„Достъпът до информация и функции е непрактичен“** — дългите процеси (backup,
   проверка на цялост, миграция, групови операции) нямат единен, постоянен индикатор
   за прогрес и резултат; резултатът изчезва след 4 секунди (настоящият `toast`).

Фаза 5 решава и двете: пълноценен екран „Настройки“ + постоянен Център за уведомления
с прогрес и състояние.

## 2. Какво вече съществува (фундамент)

| Слой | Налично | Къде |
|------|---------|------|
| Валидация на настройки | ✅ пълна, с типове и диапазони | `runtime-config.js` (`validate`, `validateLimits`, `validateData`, `validateRetention`, `validatePreview`) |
| Четене/запис | ✅ `GET`/`PATCH /admin/api/settings` | `server.js` ~377–386 |
| Ефективни стойности + рестарт | ✅ `effective()` + `restartRequired` | `server.js` ~386 |
| Профили на настройки | ✅ `config-profiles.js` + API | `server.js` ~485–503 |
| Toast (еднократно) | ✅ `toast(msg, type)` | `admin.js` ~460 |
| Опашка с прогрес | ✅ `job-manager.js` (`done/total`, pause/resume/cancel) | `server.js` `/admin/api/jobs` |

**Извод:** backend-ът вече знае всичко; липсва (а) организиран UI за настройки и
(б) постоянен, свързан с Event Bus, център за прогрес/статус.

## 3. Настройки — групи и функции

Всички ключове идват от `runtime-config.js` (`DEFAULT`). Групираме ги в 7 секции:

### 3.1 Бранд (QR метаданни)
| Ключ | Тип | Функция | Default |
|------|-----|---------|---------|
| `organization` | string ≤120 | Подпис „издател“ в QR landing/manifest | `PasevSU DEV` |
| `project` | string ≤120 | Проект/кампания в QR manifest | `Home Assistant Projects` |
| `campaign` | string ≤120 | Кампания (напр. NO TRUST) | `NO TRUST Cybersecurity` |

### 3.2 Съхранение
| Ключ | Тип | Функция | Default |
|------|-----|---------|---------|
| `artifactDirectory` | сегмент | Папка за QR артефакти | `qr-records` |
| `databaseDirectory` | `.`/сегмент | Подпапка на метаданните | `.` |
| `databaseFile` | `*.json` | Файл на метаданните | `db.json` |

> Смяната на `database*` изисква **рестарт** (върнато като `restartRequired`).

### 3.3 Лимити и мрежа
| Ключ | Диапазон | Функция |
|------|----------|---------|
| `maxUploadMb` | 1–2048 | Горна граница на качване (MB) |
| `maxDownloadStreams` | 1–1024 | Макс. конкурентни изтегляния |
| `maxJobs` | 1–4 | Конкурентност на опашката |
| `storageCheckMinutes` | 0–10080 | Период на проверки на хранилищата (0 = off) |
| `publicBaseUrl` | URL | Външен базов URL за публични линкове |
| `corsOrigin` | URL | CORS origin (празно = изкл.) |
| `requirePortalToken` | bool/null | Задължителен портален токен |
| `storeRawIp` | bool/null | Запис на необработен IP в телеметрия |

> `maxDownloadStreams`, `maxJobs`, `storageCheckMinutes`, `corsOrigin`,
> `requirePortalToken`, `storeRawIp` влизат в сила след **рестарт** (startup keys).

### 3.4 Данни / таксономия
| Ключ | Стойности | Функция |
|------|-----------|---------|
| `conflictPolicy` | `queue`/`first`/`skip` | Поведение при дублиране (също при миграция) |
| `strictTaxonomy` | bool | Само познати категории/групи |
| `defaultCategory` | string ≤120 | Категория по подразбиране |
| `defaultGroup` | string ≤120 | Група по подразбиране |
| `maxTags` | 1–100 | Макс. тагове на файл |

### 3.5 Retention (съхранение/изтриване)
| Ключ | Стойности | Функция |
|------|-----------|---------|
| `enabled` | bool | Дневен retention цикъл |
| `fileDays` | 1–36500/null | Възраст за действие върху файлове |
| `auditDays` | 1–36500/null | Възраст за подрязване на одит |
| `fileAction` | `disable`/`delete` | Действие върху изтекли файлове |

### 3.6 Предпреглед
| Ключ | Стойности | Функция |
|------|-----------|---------|
| `enabled` | bool | Разрешава `/preview` |
| `thumbnails` | bool | Разрешава `/thumbnail.svg` |

### 3.7 Резервни копия (график)
| Ключ | Стойности | Функция |
|------|-----------|---------|
| `backupSchedule.enabled` | bool | Периодично backup |
| `backupSchedule.intervalMinutes` | 1–525600 | Интервал |
| `backupSchedule.maxBackups` | 1–1000 | Брой запазени копия |

### 3.8 Опции на добавката (само за четене / препратка)
`config.yaml` `options`: `token`, `db_id`, `username`, `password`, `db_name`,
`backup_folder`, `profiles`. Те се показват в отделен панел „Add-on“, редактират се в
Supervisor (не в admin UI), а `db_id` се използва в композитния ключ.

## 4. Дизайн на екрана „Настройки“

- **Ляв списък със секции** (7+1 групи от §3); **дясна форма** с полета, обяснения и
  текущата ефективна стойност (`effective()`).
- **Валидация на място** — използва същите правила като backend; грешката показва
  диапазона (напр. „1–2048“) още преди `PATCH`.
- **Бейдж „Reстарт“** — полетата, които влизат в сила след рестарт, са маркирани; след
  запис се показва банер „Изисква рестарт“ според `restartRequired`.
- **Профили** — „Запази като профил“ / „Приложи профил“ използват съществуващия
  `config-profiles` API (drop-down + сравнение „текущо vs профил“).
- **Запис** — единичен `PATCH /admin/api/settings`; при грешка 400 съобщението се
  извежда в тост/центъра за уведомления, а не се губи.

## 5. Информационен блок за прогрес/статус (Център за уведомления)

### 5.1 Изисквания
1. Постоянен (не изчезва след 4 s) — с история.
2. Показва **прогрес** (детерминиран `done/total` и недетерминиран spinner).
3. Показва **краен резултат**: успех / провал / отменен, с причина.
4. Покрива всички дълги процеси: jobs, backup/restore, проверки на цялост, миграция,
   групови операции, retention, QR dispatch.
5. Достъпен от всяко място на UI (глобален), с брояч на активни/неуспешни.

### 5.2 Архитектура

```
Process (job-manager / backup / migrate)
      │  emits
      ▼
Event Bus (event-bus.js) ──► NotificationCenter (in-memory, пръстенов буфер N=100)
      │                           │
      │ GET /admin/api/events     │ SSE /admin/api/events/stream (optional)
      ▼                           ▼
   admin.js: NotificationCenter UI (toast + drawer)
```

- **Сървър:** нов `notification-center.js` (интерфейс, както останалите модули).
  Държи пръстенов буфер от събития `{id, ts, source, type, status, done, total,
  message, errorCode}`. Записва само последните N (напр. 100) — без unbounded растеж.
- **Източници:** подписва се към `event-bus.js` за `job.*`, `backup.*`, `migrate.*`,
  `integrity.*`, `retention.*`, `qr.dispatch`; + fallback за всеки синхронен резултат.
- **Клиент:** полинг `GET /admin/api/events?since=<ts>` (просто и надеждно) + опционално
  SSE за незабавна доставка. Активните процеси се извеждат като карти с progress bar;
  завършилите — като ред със статус икона (✅/❌/⏹) и време.

### 5.3 Модел на състоянията
| Състояние | Индикация | Пример |
|-----------|-----------|--------|
| `queued` | spinner, „в опашка“ | Job №n чака |
| `running` | progress bar `done/total` | Backup 3/10 |
| `succeeded` | ✅ зелено, резултат | „Миграция: 128 файла, 0 грешки“ |
| `failed` | ❌ червено, причина + код | „Backup failed: ENOSPC“ |
| `cancelled` | ⏹ сиво | „Отменено от потребител“ |

### 5.4 Поведение
- „Център“ бутон в горната лента с брояч (активни + неуспешни).
- Клик отваря drawer (изтеглящ се панел): активни отгоре, история отдолу, бутони
  „Изчисти“ / „Покажи само неуспешни“.
- Грешка при **всяко** admin действие (не само фоновите) също се записва в центъра.

## 6. Нови API (минимални, версионирани)
| Метод | Път | Функция |
|-------|-----|---------|
| `GET` | `/admin/api/events?since&limit` | История на уведомленията |
| `GET` | `/admin/api/events/stream` | (optional) SSE |
| `POST` | `/admin/api/events/clear` | Изчистване на историята |

Всички минават `adminGate(...,'settings')` / `'audit'` по смисъл.
