# DOCFLOW — Фаза 6: Архитектура за миграция на папка с документи и указатели (0% щети)

> **Статус:** Архитектурна заложба (план за изграждане). Надгражда Фаза 5 (прогрес).
> **Базов документ:** `08-master-plan-v5.0.md` §4 (Migrate/Legacy), `10-phase-4-gap-closure.md`.
> **Цел:** Мигриране на папка с документи + указатели/директории към DOCFLOW ядрото по
> най-безопасния метод, с **0% загуба/повреда на файлове** и възможност за пълен
> откат (rollback) във всяка точка.

---

## 1. Принципи (непреговаряеми)

1. **Никога не пишем в източника.** Източникът е read-only през цялата миграция.
2. **Copy → Verify → Switch** (не move/delete). Превключваме едва след пълна проверка.
3. **Проверка по SHA-256 на всеки файл** преди и след копиране.
4. **Атомарно превключване** (atomic rename) — няма частично видимо състояние.
5. **Манифест/инвентар** — точният списък на източника се снема и сравнява с резултата.
6. **Dry-run по подразбиране** — планът се показва и потвърждава преди изпълнение.
7. **Idempotent + възобновимо** — прекъсната миграция може да се продължи без дубликати.
8. **Rollback** — при всяка фаза съществува обратен път без загуба на данни.

---

## 2. Съществуващ фундамент

| Модул | Роля | Поведение (безопасност) |
|-------|------|-------------------------|
| `storage-preflight.js` | Проверка на място/монтиране/симв. връзки/свободно място | **fail-closed** при липсващо NAS монтиране; отказва symlink |
| `storage-migrate.js` | Офлайн копиране legacy → DOCFLOW | **никога не трие източник**; SHA-256 per file; staging + atomic rename; `sourcePreserved` |
| `migration-bridge.js` | Legacy `directory/portals/cabinet` → core.sqlite | идемпотентен; пише само в отделен `core.sqlite`; meta-маркери |
| `storage-check.js` | Циклични проверки на цялост | детектира несъответствия в инвентара |
| `job-manager.js` | Опашка с прогрес | `done/total`, pause/resume/cancel (свързва се с Фаза 5) |

## 3. Архитектура — тръбопровод на миграцията

```
[1] PRECHECK   ── storage-preflight (място, mount, free-space, marker)
[2] SNAPSHOT   ── inventory + SHA-256 манифест на източника (read-only)
[3] PLAN       ── diff + стратегия + конфликти  →  DRY-RUN отчет (за потвърждение)
[4] STAGE      ── копиране в staging/ (hash-проверка на всеки файл)
[5] VERIFY     ── сверява staging срещу snapshot (брой, размери, SHA-256)
[6] SWITCH     ── atomic rename: staging → target (една операция)
[7] RECONCILE  ── регистрира указатели/директории в DOCFLOW ядрото (bridge)
[8] REPORT     ── резултат + rollback артефакти; източникът остава непокътнат
```

Всяка стъпка излъчва събития `migrate.*` към Event Bus → Център за уведомления (Фаза 5)
с `done/total` и краен статус.

---

## 4. Стратегии за трансфер (многофункционални методи)

Избираеми per-run и per-source:

| Метод | Кога | Риск | Бележка |
|-------|------|------|---------|
| **Copy + verify** | Default за всичко | най-нисък | отделно копие; източникът не се докосва |
| **Hardlink** | Същата файлова система (NAS→NAS) | нисък, но споделя inode | fallback към copy при `EXDEV` |
| **Reference (no-copy)** | Източникът остава на място (дългосрочен монтаж) | източникът остава единствен | запазва пътя; само регистрира в ядрото |
| **Move (само с явно потвърждение)** | Когато източникът трябва да бъде освободен | висок | **забранен без изричен флаг + проверка** |

Правила:
- Default = **Copy + verify**; всичко друго е opt-in с предупреждение.
- `EXDEV`/cross-device автоматично деградира hardlink → copy.
- Reference не създава второ копие и се маркира `sourcePreserved: true`.

## 5. Политики за конфликти (съвпадат с `data.conflictPolicy`)

| Политика | Поведение при дубликат |
|----------|------------------------|
| `queue` | името се суфиксира (`name (2).ext`) — нищо не се презаписва |
| `first` | запазва се съществуващото; новият се пропуска с бележка |
| `skip` | новият се пропуска; отчита се в отчета |

> Никога не презаписваме файл със същото име без изрично разрешение — това е ключът
> към 0% щети при имена-колизии.

---

## 6. Възобновяемост и контрол

- **Checkpoint:** след всеки файл се записва `migration.state` (JSON, атомарно) —
  `{planId, phase, done:[ids], lastSha, createdAt}`. При рестарт тръбопроводът
  продължава от последния чекпойнт.
- **Батчове:** `batchSize` (напр. 100 файла) + опционално `rateLimitBytes/s`, за да не
  се блокира I/O на NAS/HA.
- **Отказ:** `job-manager.cancel()` прекъсва между батчовете (не по средата на файл);
  staging се запазва за възобновяване.

## 7. Гаранции за 0% щети (чеклист по фаза)

| Фаза | Гаранция |
|------|----------|
| PRECHECK | отказ при липсващо/loose монтиране, symlink в пътя, недостатъчно място |
| SNAPSHOT | read-only readdir + `sha256sum`; без заключване на източника |
| PLAN | dry-run; показва брой файлове, общ размер, конфликти, необходимо място |
| STAGE | `copyFile` + `fsync`; hash на копието се сверява с източника преди commit |
| VERIFY | сверка на целия staging срещу snapshot; при разминаване → abort (без switch) |
| SWITCH | `fs.rename` (атомарен); target се пази като `target.bak.<ts>` до commit |
| RECONCILE | само в `core.sqlite`; meta-маркер `migratedAt`; legacy-то не се мутира |
| REPORT | `sourcePreserved: true`; rollback артефакт `target.bak.<ts>` |

**Ключова гаранция:** дори при срив в най-лошия момент източникът е непокътнат, а
целта е или старата, или новата напълно завършена версия — никога смесена.

---

## 8. Миграция на указатели/директории (legacy → DOCFLOW ядро)

Използва `migration-bridge.js` семантиката:

- `directory/` → **групи + профили** (профилът се генерира от папката, съгл. §2 на
  master плана).
- `portals/` → **portals** (QRF).
- `cabinet/` → **records/variables** (композитен ключ `{prefix}-{ID_db}-{id_gruppe}-{field}`).
- Записи без пълна връзка → **orphan** (асоциират се по-късно, не се губят).
- Всяка единица получава `migratedAt` + `sourcePath` в `core.sqlite`; legacy-то остава
  за audit.

## 9. API на миграцията

| Метод | Път | Функция |
|-------|-----|---------|
| `POST` | `/admin/api/migrate/preflight` | PRECHECK (връща OK/блокери) |
| `POST` | `/admin/api/migrate/plan` | SNAPSHOT + PLAN (dry-run отчет) |
| `POST` | `/admin/api/migrate/run` | Изпълнение (STAGE→SWITCH) — връща job id |
| `GET` | `/admin/api/migrate/:planId` | Прогрес/статус |
| `POST` | `/admin/api/migrate/:planId/cancel` | Отказ между батчове |
| `POST` | `/admin/api/migrate/:planId/rollback` | Връща `target.bak.<ts>` |

Всички минават `adminGate(...,'migrate')` и се одитират (`audit('migrate.*')`).
