## Проект: DOCFLOW – Йерархична система за обработка на документи

**Версия:** 1.0
**Дата:** 2026-10-12
**Статус:** Draft за одобрение
**Автор:** [Екип]

---

## 1. Резюме (Executive Summary)

DOCFLOW е софтуерна платформа за управление на документи, контакти и шаблони, изградена върху **йерархична структура от групи профили**, обвързана с папкова организация. Системата позволява гъвкаво асоцииране на записи към една или повече организации без дублиране на данни, чрез съставни ключове и префиксна namespace схема.

**Ключова иновация:** Записът съществува независимо от обвързването си с организация – може да бъде "свободен" (orphan) и по-късно да се асоциира, без да губи данни.

---

## 2. Цели и обхват

### 2.1 Бизнес цели
- Централизирано управление на документи, контакти и шаблони
- Елиминиране на дублиране на данни между профили
- Гъвкаво обвързване на записи към множество организации
- Проследимост на всички връзки и промени

### 2.2 Технически цели
- Йерархична структура: Група → Профил → Запис
- Съставни ключове: `{prefix}-{ID_db}-{name_folder}`
- Префиксна namespace схема (1000–5000+)
- Many-to-many връзки между записи и профили
- Възможност за orphan записи

### 2.3 Извън обхвата (Out of scope)
- Мобилно приложение (фаза 2)
- Интеграции с външни CRM (фаза 3)
- Автоматично OCR разпознаване на документи

## 3. Терминология

| Термин | Дефиниция |
|--------|-----------|
| **Група профили** (`ID_gruppe`) | Контейнер, обвързан с папка на организация (напр. DEW21) |
| **Профил** | Тип на данните в рамките на група (Указател, Картотека, Портали…) |
| **Префикс** | Числов идентификатор на типа профил (1000, 2000…) |
| **Запис** | Конкретен обект (контакт, служител, документ) |
| **Name_folder** | Име на организацията-родител |
| **Orphan запис** | Запис без обвързване към група |
| **Съставен ключ** | `{prefix}-{ID_db}-{name_folder}` – уникален идентификатор |

---

## 4. Архитектура на системата

### 4.1 Йерархичен модел (3 нива)

```
Ниво 1: ГРУПА ПРОФИЛИ (ID_gruppe, name_folder)
   │
   ├── Ниво 2: ПРОФИЛ (prefix, name)
   │      │
   │      └── Ниво 3: ЗАПИС (ID_db, данни, връзки)
   │
   └── Ниво 2: ПРОФИЛ (друг префикс)...
```

### 4.2 Префиксна схема

| Префикс | Профил | Предназначение |
|---------|--------|----------------|
| 1000 | Указател | Контакти (физически/юридически лица) |
| 1001 | Служител | Под-профил на указател (лица в организация) |
| 2000 | Картотека | Архивирани записи |
| 3000 | Портали | Уеб ресурси и достъпи |
| 4000 | Стандартни текстове | Snippet библиотека |
| 5000 | Шаблони | Шаблони за документи |
| 6000+ | Reserved | Бъдещи разширения |

### 4.3 Принцип на съставния ключ

Всеки запис се идентифицира чрез:

```
{prefix}-{ID_db}-{name_folder}
```

**Пример:**
```
1000-DB001-DEW21   →  Иван Петров, контакт в DEW21
1001-DB045-DEW21   →  Мария Иванова, служител в DEW21
2000-DOC782-DEW21  →  Договор №782, картотека DEW21
```

**Правило:** Едно и също лице може да фигурира в няколко групи с различни ID_db (напр. `1000-DB001-DEW21` и `1000-DB099-EON`).

## 7. Политика при изтриване (ключово решение)

### 7.1 Изтриване на връзка (запис ↔ група)

```
Действие: Потребителят премахва DEW21 от запис
Резултат:
  ✓ Връзката се разпада
  ✓ Записът става ORPHAN
  ✓ Данните се запазват
  ✓ Показва се индикатор "Необвързан"
```

### 7.2 Изтриване на група с деца

Три възможни политики – **препоръка: B + предупреждение**

| Политика | Описание | Препоръка |
|----------|----------|-----------|
| A. Cascade | Изтрива всички деца | ✗ Не се препоръчва |
| B. Orphan | Децата остават без родител | ✓ **Default** |
| C. Block | Забрана при налични деца | ✓ Опция за Admin |

**UI поток:**
```
[Изтрий DEW21] → Modal:
  "Групата съдържа 47 записа.
   ○ Премести ги като необвързани (default)
   ○ Изтрий всичко (изисква потвърждение)
   ○ Отказ"
```

## 8. Модел на данните

### 8.1 Логическа схема (ER)

```
┌─────────────┐         ┌──────────────┐
│   GROUPS    │1───────*│   PROFILES   │
│ id_gruppe PK│         │ prefix PK    │
│ name_folder │         │ id_gruppe FK │
│ created_at  │         │ name         │
└─────────────┘         └──────────────┘
       │                        │
       │                        │
       │1                      *│
       │                        │
       │         ┌──────────────┴──────┐
       │         │                     │
       └────────*│      RECORDS        │
                 │ id_db PK            │
                 │ prefix FK           │
                 │ id_gruppe FK NULL   │
                 │ name, adresse, ...  │
                 └─────────────────────┘
                          │
                          │*
                          │
                 ┌────────┴─────────┐
                 │ RECORD_PROFILES  │
                 │ id_db FK         │
                 │ prefix FK        │
                 │ PK(id_db,prefix) │
                 └──────────────────┘
```

### 8.2 SQL DDL (опростено)

```sql
CREATE TABLE groups (
    id_gruppe    SERIAL PRIMARY KEY,
    name_folder  VARCHAR(100) NOT NULL UNIQUE,
    created_at   TIMESTAMP DEFAULT NOW()
);

CREATE TABLE profiles (
    prefix       INTEGER PRIMARY KEY,
    id_gruppe    INTEGER REFERENCES groups(id_gruppe) ON DELETE CASCADE,
    name         VARCHAR(100) NOT NULL,
    is_system    BOOLEAN DEFAULT TRUE
);

CREATE TABLE records (
    id_db        VARCHAR(50) PRIMARY KEY,
    prefix       INTEGER REFERENCES profiles(prefix),
    id_gruppe    INTEGER REFERENCES groups(id_gruppe) ON DELETE SET NULL,
    name         VARCHAR(255),
    adresse      TEXT,
    ulica        TEXT,
    postenski_kod VARCHAR(20),
    grad         VARCHAR(100),
    telefon      VARCHAR(50),
    email        VARCHAR(255),
    website      VARCHAR(255),
    country      VARCHAR(100),
    notice       TEXT,
    created_at   TIMESTAMP DEFAULT NOW(),
    updated_at   TIMESTAMP DEFAULT NOW()
);

CREATE TABLE record_profiles (
    id_db        VARCHAR(50) REFERENCES records(id_db) ON DELETE CASCADE,
    prefix       INTEGER REFERENCES profiles(prefix),
    linked_at    TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (id_db, prefix)
);

CREATE INDEX idx_records_group ON records(id_gruppe);
CREATE INDEX idx_records_key ON records(prefix, id_db, id_gruppe);
```

## 9. Потребителски потоци (Use Cases)

### UC-01: Създаване на нова група (папка)

```
1. Потребител → "Нова група"
2. Въвежда name_folder: "DEW21"
3. Системата създава:
   - Запис в GROUPS
   - Профили: 1000, 2000, 3000, 4000, 5000
4. Потвърждение → "Група DEW21 е създадена с 5 профила"
```

### UC-02: Създаване на контакт (указател)

```
1. Потребител → "Нов контакт"
2. Форма:
   - Име, адрес, телефон... (свободни полета)
   - Dropdown: [ -- Избор на организация -- ▼ ]
       • DEW21
       • EON
       • (без организация)
3. Потребител избира "DEW21"
4. Системата:
   - Генерира ID_db = DB001
   - Обвързва записа с prefix 1000 и id_gruppe на DEW21
   - Автоматично свързва записа с профили 1000, 1001, 2000, 3000...
5. UI показва:
   "Свързан с: [1000 ✓] [1001 ✓] [2000 ✓] [+ Добави]"
```

### UC-03: Премахване на връзка

```
1. Потребител отваря запис
2. Вижда списък със свързани профили
3. Натиска [X] на "DEW21"
4. Потвърждение → Modal:
   "Да премахнем ли връзката с DEW21?
    Записът ще остане в системата като необвързан."
5. Потвърждение:
   - DELETE FROM record_profiles WHERE ...
   - UPDATE records SET id_gruppe = NULL
   - Индикатор: "⚠ Необвързан запис"
```

### UC-04: Изтриване на група

```
1. Потребител → Settings → Groups → [Изтрий DEW21]
2. Системата проверява за деца:
   "Групата съдържа 47 записа и 5 профила."
3. Modal с 3 опции (вж. §7.2)
4. Изпълнение според избора
5. Audit log запис
```

## 10. API спецификация (REST)

### 10.1 Endpoints

| Метод | Endpoint | Описание |
|-------|----------|----------|
| GET | `/api/groups` | Списък групи |
| POST | `/api/groups` | Създай група |
| GET | `/api/groups/{id}` | Детайли група |
| DELETE | `/api/groups/{id}?policy=orphan` | Изтрий група |
| GET | `/api/records` | Списък записи |
| POST | `/api/records` | Създай запис |
| GET | `/api/records/{id_db}` | Детайли |
| PATCH | `/api/records/{id_db}` | Редакция |
| POST | `/api/records/{id_db}/link` | Свържи с група/профил |
| DELETE | `/api/records/{id_db}/link/{prefix}` | Премахни връзка |
| GET | `/api/records?orphan=true` | Само необвързани |

### 10.2 Примерен payload

**POST /api/records**
```json
{
  "prefix": 1000,
  "name_folder": "DEW21",
  "name": "Иван Петров",
  "adresse": "ул. Примерна 5",
  "grad": "Дортмунд",
  "telefon": "+49 231 123456",
  "email": "ivan@example.com"
}
```

**Response:**
```json
{
  "id_db": "DB001",
  "composite_key": "1000-DB001-DEW21",
  "id_gruppe": 42,
  "linked_profiles": [1000, 1001, 2000, 3000, 4000, 5000],
  "status": "linked"
}
```

## 16. Отворени въпроси (за решение)

1. **Може ли запис да е в две групи едновременно?**  
   → Препоръка: Да (many-to-many).
2. **Кой генерира ID_db – централно или per-prefix?**  
   → Препоръка: per-prefix sequence с префикс (DB001, DB002...).
3. **name_folder уникално глобално или per-tenant?**  
   → Зависи от multi-tenancy модела.
4. **Политика при изтриване на група – default?**  
   → Препоръка: Orphan + задължителен избор при конфликт.
5. **Версиониране на записи?**  
   → Фаза 2.
